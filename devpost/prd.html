Merge Desk

A merge you can watch and understand, for a developer whose pull request just went red because a teammate merged first. Desktop is the showpiece; the phone mirrors it for watching and deciding.

prd: approved

What scope said, and what we now know

scope: "read the two intents side by side"

An analysis of both sides: one plain line per side, with commits, files and authors one click away.

scope: "watch the proposed merge"

Options before action: combine both, or drop the older side, with one Recommended and why, and exactly whose work each option keeps or drops.

scope: "a merge that drops a side is held"

Unless you chose to drop it. Then it is a recorded decision, checked against your choice, confirmed inline once.

One screen, no page changes

1Analysis. One line per side; commits, files and authors expand.

The core journey

1. Open Merge Desk

On a computer, one screen: the repository's open pull requests on the left, conflicting ones first.

You see
Rows with title, number, author, branches, conflicting-file count and state.
Done when
Conflicting pull requests are listed first; "Can merge" is collapsed below.

2. Select the conflict

The right side shows the analysis of both sides.

You see
One plain line per side ("ours renames fetchUser", "theirs retries on 429"); commits, files and authors expand.
Done when
Both intents are readable without opening a diff.

3. See the options before anything happens

Two or three ways to resolve it, one Recommended with a reason.

You see
Combine both; keep ours and drop theirs; keep theirs and drop ours ("drop the older build" when one side is clearly older). Each says what is kept, dropped, and whose work.
Done when
Exactly one option is Recommended and every option lists its consequences.

4. Choose, and confirm drops inline

Dropping work asks once, inline, no pop-up.

You see
"Drops 2 commits in 1 file by [teammate]." Confirm with Cmd/Ctrl+Enter, or hold-to-confirm on phone.
Done when
Someone else's work is named in the confirmation; it is asked once.

5. Watch the agent work

A plain step list; the real branch is never touched during the run.

Steps
Read both sides · write the merge on a scratch copy · describe what it did · it parses · your choice was honored · the tests pass.
Done when
Every step shows queued, running, passed or failed; logs open with one click; two automatic retries, then it waits.

6. Verified, or held

Verified: Land writes the merge to the pull request's own branch and GitHub shows it can merge. Held: nothing changed.

Held shows
Which check failed, what the agent tried, the diff it produced.
Then
Pick a different option (recommendation updated) · steer and retry · discard.

7. Recorded

The row updates and the decision is kept on the pull request, in Merge Desk and on GitHub.

Record
Who, when, the option, the reason shown at the time, check results, and for drops exactly what was dropped (commits, files, authors).
Done when
Anyone opening the pull request later can see why it was resolved that way.

After the run

Checks, against your choice

It parses · your choice was honored · the tests pass.

All pass: VERIFIED

What it did and the diff, then Land. Writes to the pull request's branch; GitHub shows it can merge.

Any fail: HELD

Nothing changed on the real branch. Shows the failed check, what it tried and its diff. Pick another option, steer and retry, or discard.

Features and checks

Pull request list4 checks
  • Conflicting first: title, number, author, branches, conflicting files, state.
  • Pull requests that can merge are grouped below, collapsed.
  • Selecting a row opens its detail on the right, same screen.
  • Up/Down or J/K moves; Enter opens.
Conflict analysis3 checks
  • One plain-language line per side.
  • Expanding a side shows commits, files and authors.
  • Conflicting files open a GitHub-style diff, side by side on desktop.
Resolution options3 checks
  • Two or three options before anything runs.
  • Exactly one Recommended, with a one-sentence reason.
  • Each states what is kept, dropped, and whose work.
Intentional drops5 checks

Recorded as a decision, not a failure.

  • Inline confirmation names commits, files and whose work.
  • Cmd/Ctrl+Enter or hold-to-confirm, asked once.
  • Checks pass only if the dropped side alone is missing and nothing leaked in.
  • History shows "Dropped by [person], [time]", option, reason, what was dropped.
  • Recoverable now: the dropped branch and commits are never deleted; the record says where they are (branch, commit IDs).
Live run and checks6 checks
  • Step list with queued, running, passed, failed.
  • Read, write on scratch, describe, parses, choice honored, tests.
  • Raw log per step, one click.
  • The real branch is never changed by a run.
  • Two automatic retries, then it waits.
  • Real test suite under 30 seconds; actual result and output on screen. Tests that can't run show not run and hold the merge. Never a pass that didn't happen.
Held merges4 checks
  • Failed check, what was tried, and its diff, in plain words.
  • Other option (recommendation updated), steer and retry, discard, in that order.
  • Discard returns the pull request to Needs resolution, unchanged.
  • "Pick a different option" and "steer and retry" both work now: with the editor deferred, they are the ways out of a hold.
Landing a merge3 checks
  • Result card: what it did, full diff, one primary action, Land.
  • Land writes to the pull request's branch; GitHub shows it can merge.
  • Never the base branch; never overwrites history.
Decision record and phone3 checks
  • Every land, drop, hold and discard is recorded with who, when, option, reason, results.
  • Phone: same order, one column, detail as a full-height sheet.
  • Phone actions: pick, hold-to-confirm, land, steer, discard. No code editing.

Two modes, one product

Demo mode public, no sign-in

What judges try themselves.

  • Three prepared pull requests: one clean merge, one held, one where dropping a side is right.
  • Plays back real runs recorded from live mode: real options, steps, check results and timings.
  • Fast, free per visitor, can't break during judging. Writes nothing.
  • Labelled "Demo: recorded from a real run", with Reset.

Live mode sign-in, the learner only

What the video shows.

  • The real agent on a real repository the learner owns.
  • Real checks and real landing: one held merge and one verified merge landing, on camera.
  • Other accounts are refused for now.

Same screens and same code path; demo mode only swaps the data source. Recordings are captured from live mode and re-captured when the flow changes, so the demo never shows something live can't do. The README and Devpost page say which is which.

States that matter

First use

One panel: how to connect a repository.

No conflicts

"No conflicts. Every open pull request can merge."

Running

Live step list; the row shows Running.

Held

Nothing changed; failed check, attempt, diff, next actions.

Landed

Result card stays; the row shows Landed.

Changed during review

New commits arrive: marked out of date; fresh run required before Land.

Already mergeable

Nothing to resolve; no options shown.

Service unavailable

The step fails with the reason in plain words; nothing is written; retry.

Permissions

Demo mode: anyone, writes nothing. Live mode: sign-in, the learner only, repositories they can write to.

Demo reset

Reset returns the three demo pull requests to their start.

NOWBuilding for the proof of concept

  • Everything under Features and checks, for one repository (merge-desk for the demo).
  • Desktop one-screen layout and the phone layout.
  • Keyboard: J/K, Enter, Cmd/Ctrl+Enter.
  • Sheets and hold-to-confirm on the phone web view.
  • Demo mode and live mode.
  • From a hold: pick a different option, steer and retry, discard.

DEFERREDRequested, not needed to prove the kernel

  • Side-by-side editor: a held run links to the scratch copy to fix in your own editor.
  • Hand to a teammate: share the held run's page by link for now.
  • Phone notification when held: arrives with the Expo app.
  • "Restore dropped side" button: the button waits; recoverability does not (dropped branch and commits kept, location recorded).
  • Command palette: comes with the dashboard.
  • Swipe actions and haptics: a web page can't buzz an iPhone; the Expo app can.

Build priority

  1. Held merge, end to end.
  2. Verified merge, end to end.
  3. Chosen drop with its check.
  4. Options before action, with the recommendation.
  5. Everything else in the boundary.

If 1 to 3 aren't working by the halfway point: stop, report, cut from the bottom.
