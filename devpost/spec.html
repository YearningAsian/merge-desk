Merge Desk

The blueprint: Next.js on Vercel, no database. Demo mode replays real recordings; live mode runs each merge in a throwaway sandbox where git, a line-by-line check and your tests decide. The AI only proposes.

scope approved · stack reviewed

How it works, in plain language

Demo mode · anyone

Plays back recordings of real runs, saved as files in the repo, including real Lands, steering and decision-record writes captured on the demo PRs (reset afterwards). Fast, free, can't break, writes nothing. Labelled "Demo: recorded from a real run".

Live mode · YearningAsian only

Sign in with GitHub; only on merge-desk. Each run starts a throwaway cloud computer that clones the pull request, does the real git merge, writes the proposal and runs the checks, then is destroyed.

The AI's job

Gemini describes each side, suggests options and writes the merged code. It never decides: git, the line-by-line check and your tests do.

What talks to what

Browser

Desk UI with LiveSource (calls the API, reads the event stream) or RecordedSource (replays demo/recordings/*.json).

Next.js on Vercel (holds every secret)

Sign-in for YearningAsian only; every live route checks the session and that the repo is merge-desk; pipelines stream steps; Land pushes fast-forward only; one decision record per PR.

GitHub API

GitHub App on merge-desk only: contents and pull requests. No workflows permission.

Gemini 3.5 Flash-Lite

GA Interactions API, structured JSON, Zod-validated, store: false. Proposes only.

Vercel Sandbox, per run

Clone, merge, write, parse, tests with the network off. Holds no token. Destroyed after every run.

The journey, traced through the system

1. Open the desk

prd.md › Pull request list

  • /live/page.tsxChecks the session cookie; signed out shows only the sign-in panel. /demo needs nothing.
  • GET /api/live/prsGuard: session + merge-desk only. Lists open PRs (demo ones badged); mergeable_state "dirty" means conflicting; null shows "Checking".
  • ui/PrList.tsxConflicting first; "files changed on both sides" until analysis gives the exact count.

2. Analyze a conflict

prd.md › Conflict analysis

  • POST /api/live/analyzeRecords the exact start head and base SHAs.
  • runner.prepareMergeSandbox checks out the signed head, fetches the signed base, runs git merge, reads base/ours/theirs per conflicted file. Destroyed.
  • core/atoms.tsEach side's added and removed lines, renames detected. No AI.
  • gemini/analyze.tsOne-line intent per side; options. Zod-validated.
  • server/sign.tsAnalysis returned HMAC-signed, so it can't be altered between steps.

3. See the options

prd.md › Resolution options

  • core/options.tsValidates the model's 2-3 options; fills keeps/drops (commits, files, authors) from git data, not the model; labels the older side.
  • ui/Options.tsxOne Recommended with its reason.

4. Choose and confirm

prd.md › Intentional drops

  • ui/DropConfirm.tsxInline: commits, files and authors lost; names a teammate; warns if dropping the base's change will undo it when the PR merges.
  • ui/HoldToConfirm.tsxCmd/Ctrl+Enter or an 800 ms hold with cancellation and keyboard alternative. Asked once.

5. Run the checks

prd.md › Live run and checks

  • POST /api/live/runHead/base revisions unchanged? Otherwise "Pull request changed; re-run".
  • gemini/propose.tsMerged files + one-line description; steer text on retries.
  • runner.applyProposalFresh sandbox at signed revisions, merge, write, local commit; deny-all before candidate code executes.
  • runner.parseChecknode --check or trusted pinned TypeScript syntax parse; unsupported = not run, held.
  • core/honor.tsChoice honored, line by line, renames applied, unchanged regions preserved. Bounded evidence, not semantic proof.
  • runner.runTestsnode --test in playground/ if the merge only touches it, else npm run test:core; network already denied; 30 s limit; real output shown.

6. Land or hold

prd.md › Landing a merge, Held merges

  • POST /api/live/landLand guards (no forks, never main or the base, no CI workflow changes, head and base unchanged), then a merge commit via the Git Data API and a ref update with force: false.
  • ui/HeldActions.tsxFailed check, attempt, diff, Download patch; then pick another option, steer and retry, discard.

7. Record it

prd.md › Decision record

  • github/comment.tsFinds <!-- merge-desk:record --> and updates it in place; creates it only once.
  • core/record.tsWho, when, option, reason, results; for drops the branch and commit IDs. Branches are never deleted.

The run pipeline

Six steps, in order

Revisions unchanged · Propose merge (Gemini, validated) · Write on scratch · It parses · Choice honored (no AI) · Tests (network off, 30 s).

All pass: VERIFIED

Description and diff, then Land.

Any fail or not run: HELD

Nothing pushed. Download patch; other option, steer and retry, or discard.

What Land does, exactly

  1. Session is YearningAsian; repository is merge-desk.
  2. Target is the PR's own branch in this repo: not a fork, not main, not the base.
  3. The merge doesn't touch .github/workflows/ (the app has no Workflows permission).
  4. Re-read the pull request: head and base must equal the signed run revisions.
  5. Merge commit [start head, base], then move the PR branch with force: false.

Decisions, failure modes, and what to confirm

YOURSDecided

  • Cloud sandbox; 2 min per sandbox; teardown every run; verify provider spend controls; trusted laptop fallback, same code.
  • GitHub App on merge-desk only: contents and PRs; Checks dropped; no Workflows; YearningAsian only.
  • One repo: demo PRs on demo/* branches into demo/base, never main; reset script limited to demo/*; dogfood on merge-desk.
  • Held merges download as a patch; no branch.
  • Land checks the head, never force-pushes, says what it does.
  • One record comment per PR; secrets server-side; model proposes only; recordings from live runs.

CONFIRMAssumptions

  1. Held and discarded entries update the record comment (a write, never code).
  2. Demo scenarios: clean rename vs retry; held a real overlapping conflict plus a signature/call-site mismatch rejected by actual tests; drop two fixes of the same bug, keep the newer. Each seeded PR starts with a real textual conflict.
  3. "Older side" = the side whose latest commit is older.
  4. Dogfood conflict = two real feature branches of this build.
  5. The empty merge-desk-playground repo is no longer used and can be deleted.
  6. Dropping the base side is allowed with a warning that merging undoes it on the base.

Where it can break

  • Sandbox slow or down → failed step, nothing pushed, Retry; laptop runner for recording day.
  • Model output invalid or planted instructions → validation or honor check fails → held.
  • PR changed → "re-run"; Land's fast-forward is the last guard.
  • Land guard trips (fork, main or base, CI workflow files) → refused with the reason; nothing written.
  • Tests can't run → not run, held. Never a fake pass.

One useful unknown

Can a cloud sandbox clone, merge and test fast enough to watch? The first build slice times every step on the held demo scenario. Evidence: tests under 30 s, whole run under 2 min. Otherwise: dependency snapshot, fewer vCPUs, or the laptop runner.

Check early

Gemini Interactions structured output · dependency install and Next/Pierre rendering · trusted snapshot policy · actual quota/pause controls · request timing and tagged accounting · production callback URL.
