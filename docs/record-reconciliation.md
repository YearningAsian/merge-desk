# Reconcile a decision-record lock

Every Merge Desk server that writes a decision record (the laptop's dev server and every production instance) first takes one lock per pull request: a Git ref in this repository, `refs/merge-desk/locks/pr-<number>`. GitHub refuses to create a ref that already exists, so only one writer holds it at a time. Each lock points at its own root commit whose message says which pull request it is for, who held it and when.

A record write that was sent to GitHub but not confirmed keeps its lock. That prevents a late comment update from overwriting a later decision. The refusal names the lock ref. There is no expiry, automatic takeover or automatic unlock. A lock that clears within a few seconds was simply another write finishing; this procedure is for one that stays.

1. **Pause writes for the affected pull request.** Stop Land, hold and discard requests for it in every tab, on the laptop and on production. Preserve the refusal, pull request, run, comment and branch evidence. A request timeout, browser abort, function timeout or redeploy does not prove that a dispatched GitHub operation has finished.
2. **Read the exact lock.** `git ls-remote origin 'refs/merge-desk/locks/*'` lists every lock and the commit it points at. `gh api repos/YearningAsian/merge-desk/git/commits/<sha> --jq .message` shows its pull request, holder and time. Note the full commit id; it identifies this one writer.
3. **Reconcile GitHub's current state.** Use an authorized GitHub session to inspect the pull request's comments and current head/base branches. Confirm the relevant comment was authored by this GitHub App; a pasted Merge Desk marker alone is insufficient. Read the record through Merge Desk's authenticated record endpoint so its App identity, seal and pull-request scope are checked. Preserve any invalid, outside-edited or duplicate comments and their evidence. For an ambiguous Land, inspect the branch commits and parents as well; a failed record update does not undo a confirmed branch update.
4. **Resolve the outstanding remote ambiguity.** Establish whether every dispatched comment or branch operation completed, was rejected, or can still apply. A snapshot showing no new comment or commit is not enough: the earlier operation may still be pending. Do not infer completion from elapsed time, an abort, a finished function or a single successful read. If provider responses, current state and preserved evidence do not establish a settled outcome, keep the lock and seek provider or maintainer assistance. Do not retry an ambiguous writer.
5. **Unlock only after reconciliation is complete.** Read the lock again and confirm it still points at the commit noted in step 2; if it changed, another writer holds it now, so start over. Then a human operator may delete only that one ref, with their own GitHub authorization: `gh api -X DELETE repos/YearningAsian/merge-desk/git/refs/merge-desk/locks/pr-<number>`. Never delete every lock, delete any other ref, or delete or edit GitHub comments to make the refusal disappear. There is deliberately no unlock script.
6. **Read before deciding on new work.** Re-read the authenticated decision record and current GitHub branches. Keep an already completed Land as historical evidence. Start only a new, explicitly chosen action when the reconciled state permits it; unlocking does not retry or confirm the earlier operation.

The lock identifies coordination state, not a GitHub receipt or a successful decision. If reconciliation cannot establish what happened, the result remains unconfirmed and the lock stays in place. Lock refs are not branches or tags: they start no workflow, never appear in the pull request, and their commits are reachable from nothing else.
